# Zelda: Echoes of Wisdom — Turnip black screen

Opt-in diagnostic for PR #431, based on the master merge of #430
(`f0a95dd80eb150e81d16e1b0fa88c3a812a820c8`). There is no permanent
GPU fix. **Only the explicit EXPERIMENT_DEPTH_EQUAL_ALWAYS marker changes
the scene's depth compare temporarily**; without the marker, the emulator
retains the original EQUAL pipeline. This is a compact custom mini capture,
**not** a RenderDoc `.rdc` file.

## On Android

1. Install the **ARM64 DevRelease** APK generated by PR #431.
2. Launch Zelda: Echoes of Wisdom with Turnip and enter gameplay until the
   screen is already black. Do not arm during boot.
3. In Strato's public application files, open `gpu_capture/zelda_eow/`.
   Create an empty file named **`ARM_CAPTURE`**. The app polls for it once
   every ~16 presentations and consumes it automatically.
4. Continue gameplay for several seconds. A new `capture_001` (or next
   available number) folder appears with `events.jsonl`, four
   `present_source_XX_*.raw` files when supported, and completion markers.
   **Wait for `source_readbacks_done.txt`** before zipping the directory:
   the readback fence is polled on later presentations, never waited on.
5. Zip that capture directory, and send it with the matching `emulation.log`,
   the exact Turnip driver version, and a screenshot of the black gameplay.

If you want *additional* GPU-ordered render-target snapshots, create
`CAPTURE_PASS_IMAGES` next to `ARM_CAPTURE` **before arming**.
That option snapshots only single-layer, uncompressed, transfer-readable
render targets overlapping previously observed physical VI source mappings.
Wait for **both** `source_readbacks_done.txt` and
`pass_readbacks_done.txt`, then zip. If `pass_readbacks_done.txt`
reports `requested=0`, no matching pass was observed; that is not proof
that shaders rendered black.

Delete `CAPTURE_PASS_IMAGES` to return to the metadata/source-only mode.
There is no automatic ZIP creation or PNG encoding in this phase. The raw
file must be interpreted with its recorded width, height, actual VkFormat
and row/pitch-copy details; do **not** blindly treat every file as RGBA8.

## Twenty-first: revert global Z_CLIP_RANGE change after real-game regressions

**2026-11-09 user validation failed.** The experimental replacement
of Strato's viewport-derived clip-depth convention with Maxwell
`zClipRange` (method `0x35F`) **did not restore the black 3D scene**
in Zelda: Echoes of Wisdom under Turnip. It also introduced
**excessive blur under the proprietary Qualcomm driver** and
**removed shadows from Zelda: Link's Awakening**, according to the
user's direct tests. These effects are regressions, not acceptable
trade-offs for a general GPU behavior change.

**Rollback made on the existing Draft PR #431**: restore the exact
pre-change file contents from commit
`5d57ef80ddcc812d4ee3bebac983f31d210a5997` for:

- `soc/gm20b/engines/maxwell_3d.cpp`
- `gpu/interconnect/maxwell_3d/pipeline_state.h`
- `gpu/interconnect/maxwell_3d/pipeline_state.cpp`

The historical commits and previous mini-capture, per-draw pipeline
statistics and per-shader SPIR-V diagnostics remain intact.
No merge. Do not reintroduce the direct depth-register mapping
as a global fix based solely on code similarity with Eden.
The result demonstrates that selecting the depth conversion
cannot safely be decided by a one-line replacement without
checking source registers, supported Vulkan depth-clip mode,
shader conversion, viewport range, pipeline cache, and existing
games that rely on the current behavior.

**Next investigative direction (no immediate new APK/user test):**
compare the full depth-clip/viewport feature path and actual
per-draw state in Eden versus Strato; determine if Eden uses
native `VK_EXT_depth_clip_control` and skips shader depth
remapping on the installed Turnip, versus Strato's shader
conversion. Also inspect the known 6,924-index EOW draw's
vertex input/UBO bytes and geometry if feasible.
Do not apply speculative global coordinates, depth range,
shadow or raster-state changes. Require tests against both
Zelda games and Qualcomm/Turnip before any future correction.

## Twentieth: compare working Eden with Strato (verified register mismatch)

The user reports **Zelda: Echoes of Wisdom renders correctly in Eden
under the same Turnip 24.0.99** that renders a black 3D scene in
Strato. This means the driver is capable of rendering the game,
but does not isolate the fault between emulators.

Compared the Strato PR #431 branch with the **Eden source mirror**
`UzuCore/eden`, branch `dev`, tree
`10dbdfbee48418067e8a64612a8f18bbb16e1689`.
Eden's upstream official source is hosted on
`git.eden-emu.dev/eden-emu/eden`; the mirror is a
reference snapshot and not guaranteed byte-for-byte to match
the user's installed Eden APK.

**Definite missing register link in Strato:**

- Eden `src/video_core/engines/maxwell_3d.h` declares
  `DepthMode depth_mode` at **0x0D7C = Maxwell method 0x35F**;
  the enum is `MinusOneToOne=0`, `ZeroToOne=1`.
- Eden's `src/video_core/renderer_vulkan/fixed_pipeline_state.cpp`
  sets `ndc_minus_one_to_one` from
  `regs.depth_mode == Maxwell::DepthMode::MinusOneToOne`.
  Its `vk_pipeline_cache.cpp` uses that value for
  `Shader::RuntimeInfo::convert_depth_mode` (VertexB/Geometry).
  It also uses the same bit when building optional
  `VK_EXT_depth_clip_control` pipeline state.
- Strato **already declares the exact same method** as
  `Register<0x35F, type::ZClipRange> zClipRange` in
  `soc/gm20b/engines/maxwell_3d.h`; its enum values are
  `NegativeWToPositiveW=0`, `ZeroToPositiveW=1`.
  But before this fix, `MakePipelineStateRegisters`
  **did not pass this register to rasterization state**.
- Previously, `RasterizationState::Flush` inferred
  `packedState.openGlNdc` by checking
  `viewportClip0.minZ != viewport0.offsetZ &&
    viewportClip0.maxZ != viewport0.offsetZ`.
  This inference is unreliable: the viewport depth interval and
  translation are not an authoritative encoding of the 0..1
  versus -1..1 **clip-space convention**. In addition, only
  viewport minZ/maxZ/offsetZ changes invalidated the old
  rasterization state; a write to `zClipRange` alone
  could leave the existing pipeline-key depth bit stale.
  This bit controls SPIR-V depth conversion in Strato's
  `pipeline_manager.cpp`.
- The corresponding `PositionPass` implementation in the
  `BBlueSkyy/shader-compiler` matches Eden's relevant
  position transformation code (when
  `ReadViewportTransformState()` is false): there is no
  demonstrated missing general-purpose PositionPass.
- Eden's optional native `VK_EXT_depth_clip_control` support,
  Strato's viewport min/max depth construction, vertex format
  mappings and shader profile still differ in ways not
  validated by runtime capture. Do **not** transplant unrelated
  systems or claim their behavior has been proven wrong.
- Previous EOW tests already show changing depth compare
  EQUAL->ALWAYS, cull NONE or scalarizing the exact VS's SSBO
  reads did not restore the scene. None of those experiments
  tested the explicit 0x35F clip-depth register.

**Isolated code correction now on Draft PR #431:**

1. Forward `*registers.zClipRange` into
   `RasterizationState::EngineRegisters` instead of
   unrelated viewport0/viewportClip0 Z values.
2. Add `zClipRange` to dirty-register binding.
3. Compute `packedState.openGlNdc` using
   `zClipRange == NegativeWToPositiveW`.
4. Preserve existing pipeline-key layout, SPIR-V generation,
   viewport transform, shader and guest state, depth compare,
   cull mode, and all unrelated GPU features.

This is a direct **register-accuracy fix**, not a heuristic
driver-specific workaround. However, we have not captured
the **runtime value** of `zClipRange` for EOW scene draws.
It remains **unproven** that the old heuristic disagreed
with the real register during the failing game frame,
or that this correction resolves the black screen.

**Validation gate:** ARM64 DevRelease CI and existing GPU
regression tests first. Then at most one user-side EOW
Turnip gameplay check on the new APK, with all
`EXPERIMENT_*` markers removed, followed by a quick
normal-game regression if gameplay changes. If unchanged,
do not infer a different issue is solved or start more
trial-and-error patches; next evidence should be paired
vertex/index/CBUF data and pipeline viewport values for the
exact 6924-index draw, or a faithful paired draw capture.

Keep Draft, no merge.

## Nineteenth: paired scene vertex-shader binaries and controlled SSBO-lowering A/B

The user sent four independent artifacts:
`PROP.log`, `TURNIP.log`, `scene_shader_dumps PROP.zip`,
and `scene_shader_dumps TURNIP.zip`. Both use the same Strato
PR #431 shader dump code. Confirmed:

- The **guest Maxwell VS binary is byte-identical**:
  `10,664 bytes`, SHA-256
  `bac64e93988c43e14d8fc246f3c2343ff86dabcd4d74eea4bde360211f34bdd4`.
  Both logs show the same program loaded without update/DLC.
- Qualcomm proprietary 0.777.0 emits **two host variants**:
  `94,688` and `95,068` bytes (SPIR-V 1.4).
- Mesa Turnip 24.0.99 emits **two distinct host variants**:
  `87,712` and `88,092` bytes (SPIR-V 1.4).
- The first Qualcomm variant has **5,075 instructions**,
  first Turnip variant **4,725** (SPIR-V word-header iteration).
  The former has 63 `OpCompositeConstruct`, 137 `OpIAdd`,
  134 `OpShiftRightLogical`; Turnip has 0, 68 and 65
  respectively. Qualcomm has 2 separately declared `ssbo0`
  views at descriptor binding 8, Turnip has 1. The same
  relative differences recur in variant 01.
- Both versions declare `gl_Position` as output built-in
  `Position` and include four component stores. A basic
  SPIR-V SSA dependency walk through those stores reaches
  the `ssbo0` storage-buffer resource, constant buffer C4,
  vertex attribute 0 and other inputs on **both drivers**.
  Thus the diverging storage read strategy is on a dependency
  path for clip-space position; the dumps cannot establish
  whether actual runtime values differ or which concrete
  SSBO read controls a given vertex.
- In the fork's `TraitManager::QuirkManager`, **Qualcomm
  proprietary sets `brokenSpirvVectorAccessChain=true`**
  and **Mesa Turnip leaves it false**. In the paired
  `BBlueSkyy/shader-compiler`
  `backend/spirv/emit_spirv_memory.cpp`,
  `EmitLoadStorage128` and `EmitLoadStorage64` use
  direct vector access chains only if descriptor aliasing is
  supported and
  `!profile.has_broken_spirv_vector_access_chain`;
  otherwise they use multiple 32-bit loads followed by
  `OpCompositeConstruct`. This directly explains the
  scalarization/vectorization distinction in the binaries.
- Independent differences in supported Int8, subgroup size and
  other profile fields also exist, so these modules need not
  become byte-identical even if their SSBO strategy matches.
- Qualcomm log shows 299 cached graphics pipelines loaded,
  Turnip 0; the two dumps may have differing creation order,
  and variant 00/01 is not yet bound conclusively to a
  particular measured draw in the earlier GPU capture.
- Turnip logs include two `VK_ERROR_OUT_OF_POOL_MEMORY`
  messages. They remain unproven as the cause of clipping.

This is **not proof that vector SSBO access is incorrect**,
but it is now a concrete, low-risk discriminator.

In a single six-frame capture the diagnostic selects at most

shader pair, writing `pipeline_stats_XX.txt` with:

- `ia_primitives`: input-assembly primitive count
- `vs_invocations`: vertex shader invocations
- `clip_invocations`: primitives entering clipping stage

- `fs_invocations`: fragment shader invocations

Vulkan's implementation-dependent accounting, especially on
tile-based GPUs, means these are stage-level clues, not direct
per-triangle shader output or guaranteed comparable absolute
counts between vendors. Crucially, each query spans **one draw**
and is distinct from any active guest occlusion query. It neither

## Output

- `events.jsonl`: sequence of CPU-observed diagnostic events, including
  `GPU_PROPERTIES`, `PRESENT_BACKING`, `PRESENT_CHAIN`, `RP_BEGIN`,
  `RP_COLOR`, `RP_END`, `DRAW`, `FERMI_BLIT`,
  `PRESENT_READBACK_QUEUED`, and optional `PASS_READBACK_QUEUED`.
- `present_source_XX_...raw`: source image contents recorded **in the same
  GPU submission as the existing presentation copy**, *after* its normal
  source layout transition. No extra submission or CPU fence wait.
- `pass_XX_...raw` and `pass_XX.txt`: optional attachment readbacks queued
  after a naturally existing render-pass end, not after forced draw boundaries.
- `source_readbacks_done.txt`: source completion counters;
  `pass_readbacks_done.txt`: optional pass completion counters.
- `capture_complete.txt`: metadata collection finished; by itself it
  does **not** guarantee that asynchronous file writes finished.

A matched physical mapping is a useful link from VI to the render target,
**not** proof of the last GPU writer. `events.jsonl` records asynchronous
CPU observations, not a perfectly ordered GPU timeline. If the last writer
cannot be uniquely identified, the next capture must narrow the specific
attachment, render pass and draw. Do not infer black pixels from a metadata
entry; inspect readbacks.

## Bounded overhead

- Four approximate presentations per arm; no boot trace.
- At most four source readbacks of 12 MiB each.
- Optional: at most 12 pass images, 64 MiB combined, 4 per interval,
  each at most 12 MiB.
- At most 10,000 in-memory event records; written at capture end.
- No fixed game ID, no global rendering/synchronization fix, no modified
  descriptor behavior, no extra render-pass split, and no additional
  presentation-thread fence wait.
- Image copies and disk I/O **only while explicitly armed** can still affect
  timing. If arming changes the visual bug, that is a diagnostic limitation;
  report it rather than treating it as a correction.
