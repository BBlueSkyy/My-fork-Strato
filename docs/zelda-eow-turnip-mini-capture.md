# Zelda: Echoes of Wisdom — Turnip black screen

Opt-in diagnostic for PR #431, based on the master merge of #430
(`f0a95dd80eb150e81d16e1b0fa88c3a812a820c8`). There is no permanent
GPU fix. **Only the explicit EXPERIMENT_DEPTH_EQUAL_ALWAYS marker changes
the scene's depth compare temporarily**; without the marker, the emulator
retains the original EQUAL pipeline. This is a compact custom mini capture,
**not** a RenderDoc `.rdc` file.

## On Android

1. Install the **ARM64 DevRelease** APK generated by PR #431.
2. Launch Zelda: Echoes of Wisdom with Turnip and enter gameplay until the
   screen is already black. Do not arm during boot.
3. In Strato's public application files, open `gpu_capture/zelda_eow/`.
   Create an empty file named **`ARM_CAPTURE`**. The app polls for it once
   every ~16 presentations and consumes it automatically.
4. Continue gameplay for several seconds. A new `capture_001` (or next
   available number) folder appears with `events.jsonl`, four
   `present_source_XX_*.raw` files when supported, and completion markers.
   **Wait for `source_readbacks_done.txt`** before zipping the directory:
   the readback fence is polled on later presentations, never waited on.
5. Zip that capture directory, and send it with the matching `emulation.log`,
   the exact Turnip driver version, and a screenshot of the black gameplay.

If you want *additional* GPU-ordered render-target snapshots, create
`CAPTURE_PASS_IMAGES` next to `ARM_CAPTURE` **before arming**.
That option snapshots only single-layer, uncompressed, transfer-readable
render targets overlapping previously observed physical VI source mappings.
Wait for **both** `source_readbacks_done.txt` and
`pass_readbacks_done.txt`, then zip. If `pass_readbacks_done.txt`
reports `requested=0`, no matching pass was observed; that is not proof
that shaders rendered black.

Delete `CAPTURE_PASS_IMAGES` to return to the metadata/source-only mode.
There is no automatic ZIP creation or PNG encoding in this phase. The raw
file must be interpreted with its recorded width, height, actual VkFormat
and row/pitch-copy details; do **not** blindly treat every file as RGBA8.

## Fourteenth experiment: combined depth ALWAYS + cull NONE

A second A/B test on Turnip 24.0.99 verified culling was actually
disabled on the pinned scene pipeline: `matched_pipeline_updates=84`,
`matched_scene_draws=114` and `CULL_NONE_DRAW` records were present.
Nevertheless the scene remained black (0–92 nonzero HDR pixels in a
1280x720 target). Existing guest query segment submit 546 RP 23 had
`samples=0, available=1`, with 18 scene-cull-none draws and 10 other
guest draws. This **zero** rules out passing occlusion samples anywhere
in that segment; the query is correctly labeled mixed and is *not* an
isolated scene draw count. Another mixed query spanning the depth
prepass recorded 1,182,706 samples, demonstrating some rasterized
geometry in that segment but not individually attributing them to
the 31 observed depth-prepass draws.

The previous depth-ALWAYS and cull-NONE tests changed **only one
condition at a time**. To determine whether BOTH conditions jointly
exclude fragments, a third independent A/B marker is now available:

`EXPERIMENT_SCENE_DEPTH_ALWAYS_CULL_NONE`

It is created empty in `gpu_capture/zelda_eow/`. Remove the older
`EXPERIMENT_DEPTH_EQUAL_ALWAYS` and `EXPERIMENT_SCENE_CULL_NONE`
markers first for clarity. The new mode applies both Vulkan
`depthCompareOp=ALWAYS` and `cullMode=NONE` **only** to the known
EOW scene shader pair (VS `A8A68D4DADC852BA`,
FS `01432EB691C0F662`) when all original conditions match:
depth test enabled, depth write off, original compare EQUAL,
original culling not NONE, D24UnormS8Uint depth target and
1280x720 B10G11R11UfloatPack32 HDR target.

The existing PackedPipelineState key creates a separate cached
Vulkan pipeline for this combined variant. On removal, both original
depth compare and culling are restored from the guest registers
before lookup. The new marker overrides the older two if they
are present. No shader, guest register, prepass or unrelated
pipeline is changed.

For an exact capture, keep all four standard marker files:
`ARM_CAPTURE`, `CAPTURE_PASS_IMAGES`, `CAPTURE_SCENE_PRODUCER`,
`CAPTURE_SCENE_OCCLUSION`. Record the visual result in gameplay
and wait for the three readback completion files.

New evidence:
- `scene_depth_cull_bypass_experiment.txt` shows if the new
  pipeline and actual scene draws were matched
- `DEPTH_CULL_BYPASS_PIPELINE` and `DEPTH_CULL_BYPASS_DRAW`
  are bounded event records
- `occlusion_XX.txt` now contains `scene_combined_draws`;
  when the query includes any non-scene or different-mode draws,
  it is explicitly marked `mixed=true`
- Only `available=1` represents valid GPU sample results.

If the combined variant restores samples when both isolated
experiments did not, investigate the interaction between depth
and triangle orientation. If combined still yields zero samples,
look earlier in the pipeline (vertex clipping, viewport,
vertex/fragment shader kills, or conditional/descriptor issues)
and avoid inventing a depth-only or cull-only fix.

**Remove the combined marker after the test.** This remains a
diagnostic, unmerged PR.

## Eleventh capture: reuse the game's existing occlusion segments

The extra `OCCLUSION_FILTER` data from Turnip 24.0.99 resolves the
zero-query mystery. Out of 31 qualifying indexed scene draws, 30
matched the dynamically discovered depth attachment and the
EQUAL-tested scene color pass. **All 30 had
`sample_counter=1`; 29 had `guest_query_open=true`.**
Thus zero independent occlusion queries were scheduled by design,
to avoid nesting Vulkan queries of the same type. The GPU results
themselves remain unknown; the 0 requested queries were **not**
zero passed samples. The 6/6 source and 6/6 scene-color readbacks
succeeded. Scene color remained 0, 0, 16, 92, 92, 92 nonzero
pixels across its six snapshots.

The revised diagnostic uses the **existing guest occlusion query
segments** instead of starting a second Vulkan query. The Maxwell
draw hook tags a live guest query segment when it contains an
observed `scene_color_equal` or `scene_depth_prepass` draw.
At the segment's existing `endQuery`, the diagnostic adds an
optional second `copyQueryPoolResults` with
`64_BIT|WITH_AVAILABILITY` to a private staging buffer after the
**natural RP end**, leaving the game's own result-buffer copy and
query accumulator untouched. Nothing changes the guest's query
begin/end, its reports, the framebuffer, shaders or depth tests.
No CPU GPU fence wait, new query pool, query reset or forced pass
split is introduced by the guest-segment observer.

`occlusion_XX.txt` is tagged
`source=guest_query_segment`, including the submission,
render pass, guest query index, number of *identified scene draws
in the segment*, and its reported samples/availability.
A segment may cover multiple draws; its result is **not**
a per-draw sample count. Only `available=1` is interpretable.
The same opt-in `CAPTURE_SCENE_OCCLUSION` marker is used;
the existing query count caps remain intact.

If any draws have no active guest occlusion query, the previous
independent, non-nested probe remains available. Capturing Turnip
first should determine whether its color pass reports nonzero
samples. For quantitative A/B comparison, repeat the same
capture with the Qualcomm proprietary driver afterward.

## Tenth capture: explain zero selected queries on Turnip

With `CAPTURE_SCENE_OCCLUSION` enabled, Turnip 24.0.99 armed a scene
capture at ~31.67 s, and wrote **12/12** scene-color snapshots and
**6/6** VI readbacks successfully. Both VI intervals show the same
sequence: 0, 0, 16, 92, 92, 92 nonzero pixels in the `1280x720`
scene texture. No occlusion files were emitted:
`occlusion_readbacks_done.txt` reports
`requested=0, prepass_selected=0, color_selected=0`.
There were **21 SCENE_DRAW_STATE** entries for indexed color draws
with `depth_test=true, depth_write=false, depth_func=EQUAL`.
This is a **query-selection failure**, not a zero-sample result.

The existing code excludes draws when the guest Maxwell sample
counter is enabled or a guest Vulkan occlusion segment remains
active, to avoid nested same-type queries. It also requires
the dynamically discovered scene depth texture to match the
draw's depth attachment. Those filters may be excluding the
entire window, but which one caused the failure remains unproven.

For the next capture, the same four marker files remain valid.
New bounded `OCCLUSION_FILTER` metadata records the relevant
target/depth match, guest sample-counter register, active guest
query, conditional-rendering state and transform-feedback state
for the first 32 qualified draws. The
`occlusion_readbacks_done.txt` summary also records:
`scene_indexed_draws`, `scene_with_tracked_depth`,
`color_equal_candidates`, `depth_prepass_candidates`,
`candidates_guest_counter_enabled`, and
`candidates_guest_query_active`.

The query protection has **not been relaxed**. If guest queries
are active during all scene draws, do not force another nested
occlusion query. Use the observed filter data to design a different
non-invasive comparison. This diagnostic is intentionally safe
for both Qualcomm and Turnip, and no graphics fix is implied.

## Ninth capture: independent scene occlusion queries (Turnip vs Qualcomm)

The proprietary Qualcomm driver (0.777.0, Vulkan 1.1.276) renders
approximately **287859 nonzero pixels** in the actual scene color target
after its world render pass, while Turnip 24.0.99 produces only
0–92 nonzero pixels in the corresponding target. Both drivers used
`depth_test=true`, `depth_write=false`, `depth_func=EQUAL`,
matching relevant scene shader hashes and populated sampled image
descriptors. This A/B evidence localizes the discrepancy to the
world draw/raster/depth/fragment path, **not** the final Fermi blit.
A correct output with EQUAL on Qualcomm does not prove that EQUAL is
implemented incorrectly in Turnip.

The next opt-in test adds **CAPTURE_SCENE_OCCLUSION** alongside the
three existing markers in `gpu_capture/zelda_eow/`:

- `ARM_CAPTURE`
- `CAPTURE_PASS_IMAGES`
- `CAPTURE_SCENE_PRODUCER`
- `CAPTURE_SCENE_OCCLUSION`

`CAPTURE_SCENE_DEPTH` is **not required** for this test. With the
four markers the diagnostic waits for indexed scene geometry as
before, tracks the real scene color target and its depth attachment,
and adds independent Vulkan occlusion queries on a small sample
of eligible draws:
- `role=scene_depth_prepass` for draws writing the observed depth.
- `role=scene_color_equal` for draws targeting the observed scene
  color RT using Vulkan EQUAL depth compare and no depth writes.

These are separate `vk::QueryPool` objects and staging buffers,
not the guest/NVN occlusion-query machinery. The instrumentation
skips a draw if guest occlusion is active, and it never changes
the depth function, culling, shaders, or color writes. The
queries are reset before the command buffer's RPs, begin/end
around the selected draw itself, and copied using
`64_BIT | WITH_AVAILABILITY` **without WAIT** after its existing RP
ends. The result callback runs after the normal fence-cycle waiter,
with no diagnostic CPU fence wait. Each class samples at most
12 draws across later VI intervals, 24 probes total.

Files `occlusion_00.txt`, `occlusion_01.txt`, etc contain the
driver-agnostic draw role, shader hashes, indexed element count,
render-pass index, `samples` and `available`. Wait for
`occlusion_readbacks_done.txt` as well as
`source_readbacks_done.txt` and `pass_readbacks_done.txt` before
zipping the full capture and `emulation.log`.

Only compare samples with `available=1`. When `precise=false`,
a nonzero count is meaningful but the numeric count may be
implementation-dependent. If the scene-depth prepass reports
nonzero samples on both drivers but EQUAL-tested color draws
report zero only on Turnip, investigate depth value reproduction,
viewport/depth range, and SPIR-V position. If color draws report
samples on both but Turnip color RT stays black, focus on
fragment-shader/descriptor/output behavior instead.

No game or driver behavior is patched. Remove
`CAPTURE_SCENE_OCCLUSION` after collecting the A/B captures.

## Eighth capture: verify the depth prepass for EQUAL-tested scene draws

The seventh capture (Turnip 24.0.99, arm at ~29.05 seconds) captured
6/6 scene color passes and 6/6 presented VI images successfully.
The scene target at `1280x720 B10G11R11UfloatPack32` had
0, 0, 16, 92, 92, and 92 nonzero pixels after submit/RP
275/2, 275/23, 276/0, 276/9, 276/10, and 276/11 respectively.
The six final VI images are all black opaque in the 1280x720 crop.

The 21 `SCENE_DRAW_STATE` observations include indexed geometry with
up to 6924 indices, and show the same relevant pipeline state:
`depth_test=true`, `depth_write=false`, `depth_func=2`,
`discard=false`, `cull=2`, `condition=false`,
`stencil_test=false`, `alpha_test=false`, all color masks `F`.
Eight or nineteen sampled views were present per draw,
with zero null views. The depth attachment is consistently
`D24UnormS8Uint` (1280x720, one mip/layer, sample count 1,
layout `General`, `transfer_src=true`).
In the repo, `PackedPipelineState::GetDepthFunc()` casts the packed
value to `vk::CompareOp`; Vulkan compare value **2 means EQUAL**.
Therefore scene color draws require depth values to match an earlier
depth prepass exactly. This is a **strong diagnostic lead**, not yet
proof of a failed depth prepass, mismatch or driver bug.

**Depth-plane mode:** To collect evidence, create the four empty files
`ARM_CAPTURE`, `CAPTURE_PASS_IMAGES`,
`CAPTURE_SCENE_PRODUCER` and **`CAPTURE_SCENE_DEPTH`** in
`gpu_capture/zelda_eow/`. The last file is a new opt-in switch;
without it, the old capture behavior is unchanged.

In this mode, the existing live VI -> final HDR -> composition ->
upstream scene target discovery identifies the actual depth attachment
used by the scene. The debugger can then read that same depth texture
at existing pass endings (including depth-only passes) using a
`VK_IMAGE_ASPECT_DEPTH_BIT`-only `copyImageToBuffer`. For
`VK_FORMAT_D24_UNORM_S8_UINT`, the Vulkan copy's depth aspect uses
**four bytes per pixel**, equivalent to
`VK_FORMAT_X8_D24_UNORM_PACK32`; the low 24 bits are depth and
the high eight bits are undefined. **The stencil aspect is not
captured**. The generic multi-aspect texture readback method is
intentionally not used for this format.

The six-frame geometry-gated window remains unchanged. Depth mode
reserves up to three **color** and three **depth** snapshots,
under the existing max 12 snapshots / 64 MiB cap. The files have
`role=scene_producer_target` or `role=scene_depth_only`.
Look for `SCENE_DEPTH_TRACKED` and `DEPTH_READBACK_QUEUED` in
`events.jsonl`. Wait for both `pass_readbacks_done.txt` and
`source_readbacks_done.txt` before zipping the capture with
`emulation.log`. If no depth raw file exists, that does not prove the
depth buffer has zero values.

This readback records an extra transfer command **only while the marker
is present**, after a naturally completed RP; it never changes the
game's depth compare op, shaders or raster pipeline. It adds no CPU
fence wait and no forced render pass split. Remove
`CAPTURE_SCENE_DEPTH` to restore prior behavior.

## Output

- `events.jsonl`: sequence of CPU-observed diagnostic events, including
  `GPU_PROPERTIES`, `PRESENT_BACKING`, `PRESENT_CHAIN`, `RP_BEGIN`,
  `RP_COLOR`, `RP_END`, `DRAW`, `FERMI_BLIT`,
  `PRESENT_READBACK_QUEUED`, and optional `PASS_READBACK_QUEUED`.
- `present_source_XX_...raw`: source image contents recorded **in the same
  GPU submission as the existing presentation copy**, *after* its normal
  source layout transition. No extra submission or CPU fence wait.
- `pass_XX_...raw` and `pass_XX.txt`: optional attachment readbacks queued
  after a naturally existing render-pass end, not after forced draw boundaries.
- `source_readbacks_done.txt`: source completion counters;
  `pass_readbacks_done.txt`: optional pass completion counters.
- `capture_complete.txt`: metadata collection finished; by itself it
  does **not** guarantee that asynchronous file writes finished.

A matched physical mapping is a useful link from VI to the render target,
**not** proof of the last GPU writer. `events.jsonl` records asynchronous
CPU observations, not a perfectly ordered GPU timeline. If the last writer
cannot be uniquely identified, the next capture must narrow the specific
attachment, render pass and draw. Do not infer black pixels from a metadata
entry; inspect readbacks.

## Bounded overhead

- Four approximate presentations per arm; no boot trace.
- At most four source readbacks of 12 MiB each.
- Optional: at most 12 pass images, 64 MiB combined, 4 per interval,
  each at most 12 MiB.
- At most 10,000 in-memory event records; written at capture end.
- No fixed game ID, no global rendering/synchronization fix, no modified
  descriptor behavior, no extra render-pass split, and no additional
  presentation-thread fence wait.
- Image copies and disk I/O **only while explicitly armed** can still affect
  timing. If arming changes the visual bug, that is a diagnostic limitation;
  report it rather than treating it as a correction.
