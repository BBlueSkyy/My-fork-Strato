The [original scheduler investigation](mk11-scheduler-yield-progress.md) is

## Findings and proof boundary

Two general defects were reproduced and corrected. Neither host reproduction
proves that MK11 now boots consistently or reaches gameplay on Android.

1. `GetOptimalCoreForThread` inspected both its source queue and candidate
   queues with `empty()` outside the queue lock. Concurrent list insertion or
   removal is not synchronized by the selected thread's migration mutex.
   Besides the C++ data race, this can classify a queue using unpublished state.
   Deterministic tests hold the publication lock, start a selector, then publish
   runnable work: the original selector prematurely returns the empty topology.
   The fix locks every queue observation, including empty candidates. It retains
   the scoring, priorities, affinity rules and cooperative migration algorithm.
   Only one core lock is held at a time; the source observation lock is released
   before scanning candidates.
2. `UpdateSurface` reset the swapchain, and `UpdateSwapchain` replaced it through
   `optional::emplace`, without completing earlier asynchronous copies into its
   acquired images. A CPU presentation mutex serializes submissions but does not
   imply GPU completion. Shared Texture wrappers do not own swapchain image
   memory. Host tests executing both complete update methods reproduce destruction
   while a simulated GPU write is pending. `DestroySwapchain` now waits for
   submitted queue work under `gpu.queueMutex` before releasing old image/fence
   references and destroying the swapchain. The queue lock is released before
   resource destruction. A failed wait propagates and preserves the old swapchain,
   references and Java/Vulkan surface state. Initial surface creation has no idle
   wait, and replacing an existing surface drains only once.

The new queue idle occurs only during surface or extent/format replacement,
never during ordinary frames. This deliberately trades waiting for outstanding
work at those transitions for correct GPU-copy lifetime. Its transition latency,
FPS, frametime and memory behavior have not been measured on the Moto G100.

## Warning-screen progression and remaining freeze

The standalone emulation log is a progressing run. It confirms completed async
loads of `ui_ps_CharGrid`, `ui_ps_ArenaSelect` and `ui_ps_3DWorld`, with
`PlayerSelectSubMode` reached. The bugreport also shows these milestones during
the PID 11343 session. Repeated TSC warnings coexist with continued package
completion; they do not establish the later fault's cause. No sampler behavior,
descriptor fallback, shader compilation or guest loading behavior was changed.

There is no paired failed-warning-screen capture containing guest PCs, complete
run queues or the outstanding event/mutex condition. Host thread CPU percentages
and sleeping/running states do not distinguish a guest event wait, shader work,
GPU wait or scheduler starvation. Therefore this audit cannot identify the exact
guest transition out of `WARNING: READ BEFORE PLAYING` or prove its blocker.
No broad probes or speculative hot-path diagnostics were added: the next useful
device comparison is the same settings/cache with several boots of this build,
and a stall capture before pausing or returning from the activity. If it still
stalls, a targeted guest-PC/wait capture is needed to choose an instrumentation
point; the current evidence does not justify an arbitrary timeout or polling.

## Scheduler audit scope

Reviewed the current `SleepThread(0/-1/-2)` dispatch, caller-only idle migration,
priority/affinity checks, park/wake publication, contended deferred wake requests,
pause/resume, priority changes, timed and untimed waits, and adaptive condition
variable fallback. The original 22 regressions still pass. The three added cases
cover source/candidate queue publication and concurrent insert/remove/balance.
No additional lost wakeup or deadlock was reproduced. This is not a proof of all
possible Android signal/ARM64 interleavings: host facades do not execute guest
code, Android signals, NCE or Wwise.

The fix uses existing mutex acquire/release synchronization instead of adding
memory fences to an unsynchronized list access. No new sleeps, production
timeouts, polling, priority changes or game-specific branches were introduced.

## Validation

Passed on the final code:

- Scheduler: 25 cases with ASan/UBSan, with TSan, and 50 complete UBSan
  repetitions (1,250 cases). LeakSanitizer disabled because process inspection
  is unavailable in this environment; AddressSanitizer remains enabled.
- Presentation: 31 assertions covering detach, replacement and resize, their
  failed-wait paths, resource preservation/release, queue synchronization, and
  initial creation. UBSan: 25 repetitions / 775 assertions; ASan/UBSan and TSan
  also passed.
- Negative controls: both publication cases failed the starting scheduler;
  the starting presentation methods failed pending-write retirement assertions.
  The concurrent TSan negative control did not report the original race; only
  the deterministic publication controls are claimed as its reproduction.
- Unchanged GPU host regressions passed: submission/fence dependencies, sampled
  layout and aliases, null storage images, queries, and DRAW_TEXTURE.
- Independent code review found no blocking issue or new lock-order cycle.

Failures and unavailable checks, kept separate:

- `tests/gpu_conditional/run.py` fails to compile because its ActiveState facade
  lacks `InvalidateIndexBuffer`. Its entire test and extracted production inputs
  match master; this is pre-existing. No test was disabled or altered to hide it.
- `tests/gpu_framebuffer_cache/run.py` could not compile locally because the host
  lacks Boost headers. Vulkan headers were restored from the pinned submodule;
  a hardware/Vulkan-driver execution was not performed locally.
- The ARM64 APK is requested through the existing Actions DevRelease workflow,
  not claimed as compiled locally. The host fixtures compile complete method
  bodies against boundary facades, not the Android presentation header or APK.

## Vulkan scope and references

The [swapchain destruction requirement](https://docs.vulkan.org/refpages/latest/refpages/source/vkDestroySwapchainKHR.html)
requires acquired image uses to complete (VUID 01282). Queue access is externally
synchronized with the existing queue mutex. The change drains submitted copy
commands and uses the conventional queue-idle fallback for unextended WSI.
It does **not** claim formal presentation-engine completion: Khronos documents
that limitation and the maintenance-extension solution in
[Swapchain Semaphore Reuse](https://docs.vulkan.org/guide/latest/swapchain_semaphore_reuse.html).
No new WSI extension requirements or semaphore architecture changes are included.
